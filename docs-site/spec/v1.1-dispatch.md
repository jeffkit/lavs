# View Dispatch Protocol (v1.1)

v1.1 引入 **View Dispatch Protocol**——LAVS 从「一个 Agent 的 view」重新定位为「一种 content-type 的 view bundle」。

::: tip 实现状态（2026-07-29 更新）
v1.1 的 **tool-result dispatch 已实现**——standalone host 用 iframe 池同时挂载
多个 bundle 的 view，SSE agent-action 按 contentType 路由到对应 iframe，
每个 view 状态在切换后保留。**artifact dispatch 未实现**，作为未来集成对话宿主
时的扩展保留。详见 [协议总览](./overview) 和仓库 `docs/SPEC.md` §11。
:::

## 为什么要重新定位

v1.0 的 LAVS 绑定到「一个 Agent」——manifest 是 Agent 的脸，host 是 AgentStudio。
这有两个限制：

1. **不可移植**：换个 Agent 就得重写 manifest。
2. **单视图**：一个 host 只能显示一个 Agent 的 view，通用对话 Agent 想看多种数据做不到。

v1.1 把主抽象从「Agent」换成「**content-type**」（一种结构化数据的类型）。

## 两个核心概念

### content-type

每个 bundle 声明一个 `contentType`（如 `lavs/todo-list`、`lavs/daily-note`）。
contentType 是 bundle 的**类型标识**，与具体 Agent 无关——同一个 todo-list bundle 可以被任何 Agent 用。

### 两种 host 模式

| 模式 | 行为 | 适用 |
|---|---|---|
| **pinned** | host 固定渲染一个 bundle（v1.0 行为） | 单一用途的 Agent 面板 |
| **dispatch** | host 按 content-type 动态分发渲染多个 bundle | 通用对话 Agent，一个面板看多种数据 |

pinned 模式是 v1.0 的超集兼容；dispatch 模式是 v1.1 的新能力。

## Dispatch 工作流（tool-result dispatch，已实现）

```
Agent 调用 bundle B 的端点（lavs call / MCP lavs_call）
        │
        ▼
   Host 执行端点，拿到结果
        │
        ▼
   按 B 的 contentType 查 view registry
        │
        ▼
   渲染/刷新 B 的 view（iframe 池）
        │
        ▼
   数据隔离在 bundleDir/data/
```

关键设计点：
- **tool-result dispatch（normative）**：Agent 经 CLI 或 MCP 调端点，contentType
  由端点所属 bundle 隐含，无需额外信封
- **iframe 池**：host 同时挂载多个 bundle 的 view，切换时隐藏不销毁，状态保留
- **SSE 按 contentType 路由**：mutation 后的 agent-action 事件只发给匹配 bundle
  的 iframe，不影响其他 view
- **per-bundle 数据隔离**：每个 bundle 独立 `<bundleDir>/data/` 目录
- **artifact dispatch（future）**：Agent 在对话宿主里产出带 contentType 的 artifact
  信封，host 据此渲染——当前未实现，留作扩展

## manifest 变化

v1.1 给 manifest 加了一个可选字段：

```json
{
  "lavs": "1.0",
  "name": "todo-list",
  "contentType": "lavs/todo-list",   // ← 新增，可选，默认等于 name
  "version": "1.0.0",
  ...
}
```

`contentType` 是反向域名风格（类似 MIME type），遵循 `[org]/[type]` 模式。
不填则默认等于 `name`。
