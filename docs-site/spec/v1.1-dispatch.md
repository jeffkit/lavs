# View Dispatch Protocol (v1.1)

v1.1 引入 **View Dispatch Protocol**——LAVS 从「一个 Agent 的 view」重新定位为「一种 content-type 的 view bundle」。

::: tip 实现状态
v1.1 协议规范已完成（SPEC.md §11），但 **dispatch 算法尚未在 runtime 实现**。
当前 runtime 行为仍是 v1.0 pinned 模式。dispatch 实现是下一个里程碑。
:::

## 为什么要重新定位

v1.0 的 LAVS 绑定到「一个 Agent」——manifest 是 Agent 的脸，host 是 AgentStudio。
这有两个限制：

1. **不可移植**：换个 Agent 就得重写 manifest。
2. **单视图**：一个 host 只能显示一个 Agent 的 view，通用对话 Agent 想看多种数据做不到。

v1.1 把主抽象从「Agent」换成「**content-type**」（一种结构化数据的类型）。

## 两个核心概念

### content-type

每个 bundle 声明一个 `contentType`（如 `lavs/todo-list`、`lavs/daily-note`）。
contentType 是 bundle 的**类型标识**，与具体 Agent 无关——同一个 todo-list bundle 可以被任何 Agent 用。

### 两种 host 模式

| 模式 | 行为 | 适用 |
|---|---|---|
| **pinned** | host 固定渲染一个 bundle（v1.0 行为） | 单一用途的 Agent 面板 |
| **dispatch** | host 按 content-type 动态分发渲染多个 bundle | 通用对话 Agent，一个面板看多种数据 |

pinned 模式是 v1.0 的超集兼容；dispatch 模式是 v1.1 的新能力。

## Dispatch 工作流（设计）

```
Agent 产出 artifact（带 contentType）
        │
        ▼
   Host 接收 artifact
        │
        ▼
   按 contentType 查 view registry
        │
        ▼
   渲染匹配的 bundle view
        │
        ▼
   数据按 (conversation, contentType) 隔离
```

关键设计点：
- **artifact envelope**：Agent 产出的数据包裹在带 contentType 标识的信封里
- **view registry**：host 维护 contentType → bundle 的映射
- **per-scope 数据隔离**：每个 `(conversation, contentType)` 对有独立的数据作用域，避免串扰
- **normative fallback**：没匹配 bundle 时，按规范用表格渲染原始数据

## manifest 变化

v1.1 给 manifest 加了一个可选字段：

```json
{
  "lavs": "1.0",
  "name": "todo-list",
  "contentType": "lavs/todo-list",   // ← 新增，可选，默认等于 name
  "version": "1.0.0",
  ...
}
```

`contentType` 是反向域名风格（类似 MIME type），遵循 `[org]/[type]` 模式。
不填则默认等于 `name`。
